# e02 参考解释

1. 模型解析后的参数保存在 `run["events"][i]["arguments"]`，执行框架返回的实际结果在同一条事件的 `result` 中，落盘产物位于本次运行的工作目录。另外，`messages` 保存了模型在每一轮实际看到的工具反馈。
2. 两次调用在 `ToolCall.name` 上都是 `"write_file"`，但 `ToolCall.output` 保留了执行框架返回的状态字典：目录内写入是 `ok`，越界写入是 `denied`。只核对工具名会丢失执行是否被拦截的关键区别。
3. `error` 表示工具名和参数都通过了接口校验，但在实际执行时遇到环境错误（例如文件不存在）；`invalid` 表示工具名不存在或参数结构不符合定义，在进入处理函数之前就被拦下。
4. 不能。仅有任务描述和最终回答时，既无法恢复调用顺序，也无法确认每次调用是成功、被拒绝还是报错。`tools_called` 按顺序保留了工具名、参数和结果，外层的原始事件还额外保留了 `{step}.{index}` 位置编号。
5. 导出 `LLMTestCase` 会成功，因为空列表 `tools_called=[]` 和文本 `actual_output="完成"` 符合 SDK 的字段格式要求；但 `eval.py` 会判为未通过，因为 `tool_observed` 和 `requested_file` 都缺乏实际执行和产物证据。样本格式合法与任务通过是两件独立的事。
