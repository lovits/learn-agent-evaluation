# Chapter 1: 任务完成：先检查，再允许结束

## 问题

先看一个很小的修复任务。`shipping.py` 中有一个运费函数：1000克收费600分，之后每开始额外1000克增加200分。因此1001克已经进入下一档，应该收费800分。

初始实现却把1001克算成600分：

```python
def shipping_fee(weight_grams, expedited=False):
    extra = max(0, (weight_grams - 1000) // 1000)
    return 600 + extra * 200 + (300 if expedited else 0)
```

合同还要求：重量必须是精确的 `int`，且在1到5000之间，不能把 `bool` 当整数；`expedited` 必须是精确的 `bool`；类型错误先抛 `TypeError`，重量越界再抛 `ValueError`；加急增加300分；原测试文件必须保留。知识库可以挂载给模型查询。

困难不只是“如何修公式”，而是“什么时候可以说任务已经完成”。模型可能回答“已完成”，但文件根本没改；也可能只让三个公开例子通过，却遗漏类型和边界；甚至可能删除测试，使测试命令收集到零个用例后仍正常退出。

因此，模型停止输出只能算一个候选停止点。它不能自动证明文件已经符合合同。

## 解决方案

本课保留已有结构：第4课的真实 Agent 循环、第2课的文件工具与权限，以及第10课的动态工具池和宿主模型桥。模型仍然输出动作 JSON，工具仍然在 Docker 中执行。本课不是把 Agent 换成问答机器人，也不加入计划记忆或后台任务。

最小增量放在 `run_case` 外层：Agent 每次停止后，先检查三个公开例子以及测试文件是否原样保留。通过后，状态只写成 `ready_for_external_verification`，意思是“可以交给外部验收”，而不是“完整成功”。

公开检查失败时，状态为 `blocked`。真实检查反馈会追加到 `history`，然后沿用同一个工具池继续下一段循环。最多审查3轮，每段最多12个模型步骤。检查异常记为 `review_error`，耗尽轮数记为 `limit`，都不能伪装成完成。

Agent 产物冻结后，独立 Docker 验收器再检查其他输入。保留题不会回流给 Agent。本课还预先声明了一个明确冲突：若约束同时要求保留公开测试和删除全部测试，直接返回 `impossible`，模型调用次数为0。这是可判定的字段冲突，不是对任意自然语言目标的理解。

完整模块可分别阅读 [code.py](code.py)、[verify.py](verify.py)、[runner.py](runner.py)、[metrics.py](metrics.py) 和 [eval.py](eval.py)。

## 工作原理

数据从 Agent 的停止候选开始，经过公开审查、必要的续轮、独立验收，再进入规则指标和语义裁判。下面沿这条真实数据流阅读。

这里的 `result["status"] == "finished"` 只说明内部循环没有更多工具动作，相当于“模型举手说做完了”。它与完整合同是否满足是两件事。完整接入位置见 [code.py](code.py)。

执行结果同时比较返回值和精确类型；预期异常则比较异常类。公开阶段检查1000、2000和1001克，独立阶段另有20个保留输入，共23个行为输入。报告还保存源码哈希、源码是否改变和测试文件是否保留，为差异追踪留下证据。执行范围与资源限制见 [runner.py](runner.py)，完整机制见 [源码导读](source_walkthrough.md)。

**第3步：公开失败就带着真实反馈继续**

`GoalState.review` 把检查结果转换为明确状态。只有公开检查已评分且全部通过，才允许进入外部验收。

```python
def review(self, evidence, max_turns):
    self.reviews += 1
    if evidence["status"] == "impossible":
        self.status = "impossible"
    elif evidence["status"] != "scored":
        self.status = "review_error"
    elif evidence["passed"]:
        self.status = "ready_for_external_verification"
    elif self.reviews >= max_turns:
        self.status = "limit"
    else:
        self.status = "blocked"
# 省略：返回状态
```

若1001克仍返回600，状态就是 `blocked`。下一段循环能看到原任务、此前模型消息、工具结果和本次公开反馈，并继续使用已经发现的工具池。本课借用了 Learn Claude Code s17 的“停止位置再审查”，但没有照搬其会话恢复、后台延迟和通用目标判断。

**第4步：用外部事实生成规则分数**

独立验收完成后，可信结果通过 `metadata` 交给 `ExternalCompletionMetric`。证据结构由严格的 Pydantic 模型验证，不接受字符串形式的真假值。

```python
class ExternalCompletionMetric(BaseMetric):
    def __init__(self):
        self.threshold, self.async_mode = 1.0, False

    def measure(self, test_case, **kwargs):
        self.score, self.error, self.reason = None, None, None
        data = (test_case.metadata or {})["external_evidence"]
        self.score = evidence_score(data)
        return self.score

```

所有必需检查为真时得1；只要一个为假就得0。空检查、结构错误、执行器不适用或验收异常都记为 `unscored`，分数是 `null`，而不是0。对应的 `RagasExternalCompletion` 提供 `ascore` 和同步 `score`。这些规则指标不请求模型，本轮同步与异步结果一致。

**第5步：再让原生语义指标判断轨迹**

规则检查回答“文件是否真的合格”，语义指标则判断“给定轨迹看起来是否完成目标”。本课实际调用 DeepEval 的 `TaskCompletionMetric`：

```python
sample = LLMTestCase(
    input=REFERENCE,
    actual_output="\n".join(
        m.pretty_repr() for m in messages
    ),
)
metric = TaskCompletionMetric(
    task=REFERENCE, model=deep_judge,
    eval_mode="llm", async_mode=False, threshold=1,
)
value = metric.measure(sample, _show_indicator=False)
```

DeepEval 先抽取 `TaskAndOutcome`，再生成带浮点结论的 `TaskCompletionVerdict`。官方推荐完整轨迹；本课固定源码走兼容的 `input` 与 `actual_output` 分支，并明确序列化对话和外部检查，没有伪装成原生 SDK 轨迹。

Ragas 的 `AgentGoalAccuracyWithReference` 使用给定参考目标，`WithoutReference` 使用裁判推断的目标。二者先生成 `RagasWorkflowOutput(user_goal, end_state)`，再用 `CompareOutcomeOutput` 返回字符串 `"0"` 或 `"1"`。本轮 `MetricResult.reason` 为 `None`，实际解释保存在捕获的第二阶段结构化结果里。提示词、异步路径和校验细节见 [源码导读](source_walkthrough.md)。

**第6步：规则与裁判组合时，必需条件拥有否决权**

组合函数取两种分数的较小值。缺少任一有效分数时，结果保持未评分。

```python
def composite(rule_score, judge_score):
    if any(s is None for s in (rule_score, judge_score)):
        return {"status": "unscored", "score": None}
    if any(
        not math.isfinite(s) or not 0 <= s <= 1
        for s in (rule_score, judge_score)
    ):
        raise ValueError("Scores must be finite and within [0, 1]")
    return {"status": "scored", "score": min(rule_score, judge_score)}
```

真实误判说明了为什么不能只看裁判。`early_claim_only` 只有业务请求和实际的“已完成”回答，DeepEval 给出1，还在抽取结果中补出了未被证实的类型修复、边界处理和独立检查通过；Ragas 两种指标均为0。加入同一时刻真实的公开失败结果后，文件与 Agent 都没有重跑，DeepEval 变为0.2，Ragas 仍为0。这只是评分输入增加了证据，不能说 Agent 变好了。

讲师构造的“只修公开例子”状态通过三个公开用例，却在完整检查中失败；DeepEval 为0.35，Ragas 为0。此时 `min(0, 0.35) = 0`，规则失败不会被语义裁判的部分分抬高。更多结果见 [运行摘要](run_summary.md)。

本轮确实运行了2次模型 Agent，共12个模型响应、15个工具请求。正常路径1轮通过；另一条路径明确注入“先假报完成”的故障，首轮0个工具请求，随后修复，共2轮。它不能被解释为模型的自然故障率。两次最终产物均通过23个独立输入并保留测试。

另外，6个讲师构造状态分别检查了只改说明、删除测试、假报成功、只修公开例子、重复多加费用和使用不支持的 `import`。最后一种为未评分，不是0。4种评分投影实际产生24次裁判请求、12个指标结果、0个错误；未知模型标识和费用没有填写。冲突预检是后来单独在 Docker 中执行的，原有两次 Agent 轨迹和裁判记录没有伪装成重新运行。

工具调用成功率很高，只能说明工具层运行顺利。整项任务完成还要求业务行为、异常类型、边界条件和受保护文件同时满足。两种结论不能互相替代。

## 接下来

本课只增加了一道可靠的结束闸门：模型先提出停止，公开规则决定是否续轮，独立验收再判断完整合同，规则分数和语义裁判各自保留职责。这样，“模型说完成了”和“文件已经完成”不再混为一谈。
