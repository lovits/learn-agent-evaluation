# e16: 修过的问题，怎样留下来？

[e15](../e15_version_comparison/README.zh.md) → `e16`

> 把任务、证据和判据一起留下，下一次改动再核对。

## 问题

账单函数已经算对，最终却只回复“已完成”。如果任务还要求解释修复，文件检查通过就没有覆盖全部要求。

再改一句提示词，让回答具体一些。原问题改善了吗？空订单是否仍正确？本来就正确的实现有没有被改坏？这些问题需要同一批任务、同一套判据反复核对。

## 解决方案

把前面的机制组合起来：同一个 Agent 循环调用文件、Bash 和 TinyRAG 工具，留下实际上下文、动作和文件。每次任务都从新工作区开始。

![一个 Agent 循环连接模型、具名工具、只读知识库与交付文件](https://lovits.github.io/learn-agent-evaluation/diagrams/e16-integrated-agent-flow.svg?v=6bd1187ddf0b)

运行之外，独立检查函数行为，用 DeepEval 分别评价任务完成和上下文覆盖。任一关键条件失败就拒绝；证据或评分缺失时暂停判断，先补齐。

![补充任务，比较版本，按关键条件接受、拒绝或保留未决](https://lovits.github.io/learn-agent-evaluation/diagrams/e16-regression-gate-flow.svg?v=1c47918ea1cc)

## 工作原理

### 完整项目仍然只有一个循环

[run_case](code.py) 直接复用第5课 run_task。工具调用继续走第2课 agent_loop；search_knowledge 调 TinyRAG，结果回到 messages，再由模型决定下一步。

```text
任务 → 模型 → 工具调用？
              有：执行 → 结果回消息 → 模型
              无：停止，留下回答与产物
```

模型提出动作，Harness 执行动作。Bash 的教学拒绝列表与工作区路径检查沿用前课；它们没有构成任意恶意代码的完整安全沙箱。

[k=3、context_limit=3](code.py) 固定；知识库按 Docker 约定只读挂载。文档哈希、检索候选、实际送入模型的片段和完整响应分别记录。此处使用 TinyRAG 原生 VectorStore，向量是本地 TF-IDF 词面基线。

### 从一个失败补题

[failure_origin.json](failure_origin.json) 保留第12课的一条受控反例：真实文件行为通过，原生裁判发现最终说明不足。其动作和“已完成”回答是构造的，文件效果和裁决是真实执行的，不能称为自主模型失败。

据此补三个公开回归任务：漏乘数量、空订单错误、已正确实现。最后一题保护已有能力。任务新增了知识查询要求，因此属于派生回归题，并非把旧运行逐字重放。

新发现的失败进入 failure_candidates，状态为 needs_review。先看原始输入、轨迹、产物和裁决，再决定是任务失败、参考错误、评分问题还是接口异常。复核后才把任务与判据补进 cases.jsonl；不会自动把一次失败写成标准答案。

### 规则查得到的结果，直接检查

[evaluate_run](eval.py) 复用第12课 inspect_delivery：在执行结束后，从文件重新加载函数，检查多项金额、空订单、零数量与输入不变性，并核对 policy.txt 哈希。

```python
evidence = inspect_delivery(workspace, case["files"]["policy.txt"])
contract = score(DeliveryContract(), evidence_sample(run, evidence))
```

这些检查由评测程序执行。Agent 自己说“检查通过”，不能替代这里的观察。独立检查也只覆盖列出的行为，不能证明所有输入都正确。

运行结束、读取实现、送入知识片段和来源有效性另列。途中一个 Bash 检查失败并不必然代表最终失败；Agent 可以观察错误后修复，最终行为仍需重新检查。

### 每个指标只回答自己的问题

| 依据 | 本课判断什么 |
|---|---|
| 独立行为与哈希 | 函数是否正确，保护文件是否未改 |
| 实际工具记录 | 是否成功读取实现、取得并送入资料 |
| 显式 G-Eval | 对照任务、原始回答和独立观察，判断交付与说明 |
| ContextualRecall | 参考规范中的事实是否被实际上下文覆盖 |

G-Eval 直接读取原任务、原始最终回答、工具事件和独立观察，使用明确的0/1量表。已正确的代码可以不改，过程不必在最终文字重复，任务没有要求的仓库级测试不会额外成为扣分项。

这也承接第13、14课的发现：若语言裁判说“没看到工具过程”，先核对轨迹和样本范围。不能因为摘要遗漏，就认定 Agent 没执行，也不能为了让分数好看而改写原始回答。

第12课的 TaskCompletion 兼容路径会先提取结果摘要，再判断完成度。摘要可能丢失工具过程，因此这里用 G-Eval 显式量表直接读原始证据。ContextualRecall 复用第7课，本课用明确的1分门槛，单列 accepted，保留 SDK 原始 passed。

### 关键条件不能被平均数抵消

[gate](eval.py) 先要求每道任务都有两个版本的有效结果：

```python
if any(k not in lookup or lookup[k] is None for k in expected):
    return {"decision": "blocked", ...}
```

片段省略了理由字段。候选有确定失败时为 reject；全部通过且修复了基线失败，才是 accept_in_scope。两侧原本都通过，则只写 no_regression_observed。

一个保护文件被改坏，不能用另外两题的高分抵消。评分接口异常是未知，也不能记成业务零分。诊断字段只标出优先调查的位置；多个问题可能同时存在，还要查看分项证据。

三个任务都属于公开的 Atlas 账单题族。这是回归保护，无法替代独立留出验证，也不会自动发布或部署版本。

### 最小修复只改一句提示

候选版本在相同任务后补充：

```text
最终回复须具体说明计算规则如何修复、空订单与输入保持的处理；
准确区分实际检查与未检查，不要只回复已完成。
```

循环、工具、检索参数和评分条件都保持相同。实际模型输入与响应单独保留，不把裁判参考答案放进模型提示。

默认执行使用受控动作和明确标注的语义分，供离线回归检查接线与关键条件；加 `--live --judge` 才运行真实模型和原生语义评分。CI 运行前者，发布前语义复核另做，不能把离线通过称为真实模型质量通过。

```sh
python -m course.e16_regression.code --gate
```

1. 让函数返回固定金额，核对独立行为检查能否发现。
2. 修改 policy.txt，即使其他指标为满分，候选还能通过吗？
3. 将一条语义评分改为未知，观察 blocked 与 reject 的区别。
4. 加 `--live --judge`。若两侧都通过，说明当前样本未显示新收益，不要宣布提示词必然更好。
