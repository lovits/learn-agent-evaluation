# e12 参考解释

[练习](exercises.md) · [教材](README.zh.md)

1. `correct` 把修复后的 `total_cents` 写进了 `billing.py`，四组探针和 `policy.txt` 哈希检查全通过；`claim_only` 没有做任何写入，工作区里留下的仍是漏乘数量的旧实现，含商品的订单计算全部失败。最终回复只是一句文本声明，只能作为轨迹的一部分，必须对照独立产物与行为检查判定成功。
2. 例如 `[{"unit_cents": 175, "quantity": 2}]` 的预期金额是 `350` 分（或空订单 `[]` 预期为 `0` 分）。固定返回 `650` 的函数只在数值巧合的单一输入上正确，换成其他输入就会立刻失败。
3. 原任务明确要求不得修改传入的列表或字典。`items.pop()` 虽然算出了正确总额，却把调用方的非空列表清空，导致 `input_unchanged_1` 等检查失败。`DeliveryContract` 对所有必要条件取逻辑与，只要违背硬约束就记 `0` 分；改用通过率平均会把“破坏输入数据”稀释成高分，掩盖关键交付缺陷。
4. 应当作为必须满足的硬约束（一票否决项）。金额算对而策略文件被擅自修改，属于越界破坏受保护资源，整个任务并未合规交付。保留分项失败原因也比合并总分更容易定位违约点。
5. 列表推导式求和与显式 `for` 循环累加只是语法形式不同，输入输出与无副作用的行为完全一致。只要任务没有明确规定特定写法，就应当检查程序的行为契约，而比较完整源码字符串会误杀等价实现。
6. 最终验收以 `DeliveryContract` 等硬条件为准：只要硬约束失败，无论语义分多高，当前交付都判定为未完成。语义分与理由的价值在于辅助复核修复说明是否充分，以及检查裁判抽取是否漏掉了失败细节，保留用于诊断与后续校准（第 14 课）。
7. 都不能给出绝对证明。哈希只比对观察时点的文件字节，若 Agent 中途改写又恢复原样则难以从终态哈希察觉，需要配合完整的工具写入事件或文件系统审计日志；四组探针只验证了这四个典型场景，要提高通用覆盖度需要增加边界输入族、随机性质检查与留出测试集。
