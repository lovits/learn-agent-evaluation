# Chapter 1: 后台、调度与效率：少几步就更好吗

## 问题

假设你刚修好配送费用计算，需要运行一个较慢的回归命令：

```bash
python3 slow_tests.py
```

如果模型一直等它结束，就无法同时读取 `review.txt`。更麻烦的是，我们还要在受控时钟到达 09:01 后再次运行回归，并确认测试针对的是当前源码。

本课要区分四件容易混淆的事：

1. 命令已登记到后台。
2. 命令已经真实结束。
3. 模型已经收到定时提示。
4. 提示要求的工作已经完成并通过验收。

后台返回的 `bg_id` 只是取件号，不是检测合格证。调度确认也像快递签收通知：只能证明消息送达，不能证明收件人已经完成其中的工作。

本课冻结的实验协议包含三次相同正常任务和一次预声明的故意超时恢复。最终独立验收结果为正常路径 3/3，通过的超时恢复另行报告；没有挑选最好的一次。应用模型得到54次成功响应，摘要支持角色4次。样本很小，因此这些数字不能证明系统已经普遍稳定。

## 解决方案

运行时只把用户明确要求的慢命令放入后台。权限检查发生在启动之前，不能看见命令里有“测试”之类的词就自行猜测后台意图。

一次完整流程如下：

- `background_bash` 先返回 `bg_id` 和运行中状态。
- 父循环继续读取独立文件。
- 真实进程结束后，运行时在后续模型请求中注入一次通知。
- 调度器把09:01到期的提示保存为待交付状态。
- 模型成功收到提示后才确认交付，但仍必须再次启动真实回归。
- 独立验收器核对产物、通知、收据、终止状态和当前源码哈希。

## 工作原理

**第1步：明确请求后台执行，先拿占位结果**

`TimedPool.dispatch` 先复用原有权限判断，再核对本课只允许的命令，最后才启动任务：

```python
decision, reason = permission(
    "bash", {"command": args["command"]}, workspace, approve
)
if decision != "allow":
    return self.denied(reason)
if args["command"] != "python3 slow_tests.py":
    return self.denied("This lesson permits only the declared regression command")
result = background.start(args["command"], args["timeout_seconds"])
```

片段有省略，不能独立运行。输入是命令与超时秒数，输出类似 `{"id":"bg_ab12cd34","status":"running"}`。接入点位于 `lessons/e14_runtime/tools.py`。

这只是占位结果，原始工具调用也只有这一次结果。若把它当成“测试通过”，模型就可能在进程尚未启动完时错误结束任务。

**第2步：真实执行，并分别处理完成、错误和超时**

后台线程启动新的进程会话，使用 `communicate` 收集真实输出。超时时终止整个进程组：

```python
try:
    stdout, stderr = process.communicate(
        timeout=job["timeout_seconds"]
    )
    status = "completed" if process.returncode == 0 else "error"
except subprocess.TimeoutExpired:
    stop_group(process)
    stdout, stderr = process.communicate()
    status = "timeout"
```

片段来自 `lessons/e14_runtime/background.py`，省略了启动、持久化和最终清理。输出包含状态、退出码、标准输出和标准错误；正常结束、非零退出与超时不会混成同一种失败。

每条记录还保存开始与结束的单调时间，以及执行前后的源码哈希。若测试通过后又修改代码，旧收据就不能证明新代码通过。关闭父循环时若仍有任务运行，也不能把总体状态判为成功。

**第3步：在后续模型轮注入一次独立通知**

每次请求模型之前，运行时收集已经结束的任务，再保存真正发送的输入：

```python
notices = background.collect()
if notices:
    visible.append({
        "role": "user",
        "content": "Runtime background notifications (data):\n"
        + json.dumps(notices),
    })
inputs.append({"messages": copy.deepcopy(visible),
               "response_received": False})
```

这是 `lessons/e14_runtime/code.py` 中 `run_session` 的节选。通知属于后续参考数据，不是原工具调用的第二条 `tool_result`。`collect` 清空就绪队列，因此同一结果只通知一次。

如果模型请求失败，任务可能已经标记为已收集，却未真正被模型接收。因此验收还要在 `response_received=true` 的输入中找到对应通知，不能只检查后台记录里的 `notified`。

**第4步：把“到期、收到、做完”拆成三种状态**

调度器先轮询受控时钟，再取出待交付提示；请求失败时恢复，成功时才确认：

```python
self.scheduler.poll(self.moment)
offered = self.scheduler.take()
try:
    result = self.model(visible, tools, pool.actor)
except Exception:
    self.scheduler.restore(offered)
    raise
self.scheduler.acknowledge(offered)
```

片段省略了消息构造与异常范围。`poll` 的输入是明确时间，`take` 输出待交付定义，`acknowledge` 只表示模型成功收到提示。

五段 cron 支持 `*`、`*/N`、数字、范围和列表。日期与星期都受限时采用“或”语义，其他字段仍须匹配。状态先写临时文件，再以 `replace` 替换正式记录；重启可恢复待交付任务。

这种设计是至少一次交付：模型收到提示但确认尚未落盘时崩溃，重启后可能重复投递。它不是严格一次。进程关闭后不会继续调度，也不会补发停机期间错过的每一分钟。受控时钟只服务于有限实验，不代表生产定时器已经可靠运行。

**第5步：分别记录资源，并让效率裁判只回答效率问题**

资源账本保留真实计数，不把重叠时间简单相加：

```python
return {
    "model_request_attempts": len(attempts),
    "tool_calls": len(tools),
    "wall_elapsed_seconds": row["wall_elapsed_seconds"],
    "tool_elapsed_sum_seconds": sum(
        e["elapsed_seconds"] for e in tools
    ),
}
```

随后用固定配置调用 DeepEval 的原生指标：

```python
metric = StepEfficiencyMetric(
    model=model,
    eval_mode="llm",
    async_mode=False,
    threshold=0.7,
)
score = metric.measure(sample, _show_indicator=False)
```

两个片段均有省略，分别来自 `resources.py` 和 `eval.py`。DeepEval 会先从根输入抽取任务，再直接生成 `EfficiencyVerdict(score, reason)`，并非套用“1除以工具次数”的公式。调用方还检查分数必须是有限的 `0..1`。

本次4条真实轨迹均通过产物验收，但效率分都是0.25。低分不代表代码失败：严格模板会惩罚重复读取和额外动作，却明确不评价正确性与完整性。构造的“未执行却宣布完成”轨迹本次得0，不能据此宣称少做任务会拿高分。

Ragas 的原生控制另行验证有限重试和令牌聚合，使用0模型调用的讲师构造夹具。`max_retries=2` 在固定版本中表示包含首次在内最多尝试两次；单独的 `timeout` 字段不会被重试装饰器自动执行。构造令牌与讲师自定单价得到0.0036演示单位，不是市场价格或真实账单。缺少精确模型和价格时，真实费用保持 `null`。

**第6步：用独立验收拒绝“少做但早停”**

最终评分重新读取实际目录，并把行为验收与效率评分分开：

```python
checks = {
    "lead_finished": row["lead"]["status"] == "finished",
    "actual_files_match_report": actual == row["artifacts"],
    "all_jobs_notified_and_response_received":
        all(j["id"] in notices for j in jobs),
    "scheduled_work_actually_started_after_receipt":
        scheduled_started,
}
```

片段来自 `lessons/e14_runtime/eval.py`，完整实现还核对保护文件、测试收据、当前哈希、计划、待办和受控时钟。

如果模型收到09:01提示后立即结束，交付确认可能存在，但 `scheduled_work_actually_started_after_receipt` 会失败。类似地，父循环正常结束却仍有后台任务待执行，也不会通过总体验收。步骤少只有在产物正确、状态闭合之后才有意义。

## 相对一次模型问答的变更

| 方面 | 一次模型问答 | 本课运行时 |
|---|---|---|
| 慢命令 | 当前轮阻塞等待 | 明确请求后返回 `bg_id` |
| 真实结果 | 同一次调用中返回 | 后续模型轮注入一次通知 |
| 权限 | 调用前检查 | 仍在后台启动前检查 |
| 定时任务 | 没有持久状态 | 定义、待交付、确认、完成分开 |
| 成功判断 | 容易依赖最终回答 | 独立检查文件、状态、通知和收据 |
| 效率 | 常凭步骤多少猜测 | 记录回合、工具、重复读取、时间与实际用量 |

本课没有把上一课的任务图和子代理混入同一正式测量。这样可以单独观察后台与调度机制；完整的持久团队和工作流日志留到后续综合课程。

正式协议在运行前已经冻结：三次相同正常任务，一次故意以0.05秒触发超时并只允许一次5秒恢复；每个角色最多20个模型步骤。若修改预算或协议，必须另存新实验，不能把新结果混入旧分母。
