# e05 参考解释

1. 调大 `k` 只会提高候选列表的上限，放进更多排在后面的片段。只要 `context_limit` 仍为 1，工具依然只回填第一条，其余候选留在 `retrievals.hits` 里，模型实际收到的输入不会增加。固定查询和文档才能干净地观察到这个差别。
2. `hits` 记录检索器返回的全部候选；`emitted` 记录截断并格式化后准备通过工具消息回填的片段；`model_inputs` 记录每次成功模型调用时实际发出的完整消息历史。提高 `context_limit` 会让更多候选进入模型输入，但同时也会引入更多无关文本，文本变多并不等价于回答质量提升。
3. `context_limit` 限制的是单次 `search_knowledge` 调用的回填条数。由于当前循环保留完整对话历史，不会清理上一轮的工具返回，两次搜索的回填结果会累积在 `messages` 中，相同片段也不会自动去重。
4. 文档内容改动后，知识快照的 `sha256` 版本号会随之改变；原题目绑定的参考文档哈希不再匹配，因此 `context` 和 `expected_output` 置空，`reference_status` 变为 `source_changed_or_missing`。实际回答本身是被测对象，可能出错，不能充当独立的评判参考；同时旧运行记录应保留原来的版本号与片段，不能用新资料覆盖历史。
5. `start` 和 `end` 按 Python 字符串的字符下标记录。字符数、UTF-8 字节数与模型 token 数三者换算比例并不固定，按 token 偏移去切原字符串会截出完全错位的文字，导致片段无法追溯到原文。
6. 应当记在候选与工具回填记录中，但不能算进模型的实际上下文。因为没有发生下一次成功模型调用，模型从未见过这批新增片段。只在成功调用后保存 `model_inputs` 快照，正好用来区分“工具已经准备好返回”和“模型已经实际收到”。
