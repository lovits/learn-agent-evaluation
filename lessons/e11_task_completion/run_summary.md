四个明确投影共实际请求24次裁判，12个原生指标结果，0个指标运行错误。每个原生指标两次请求，抽取结果和判断结果均保留。下表是本次自动裁判结果，没有人工金标。

早期声明投影只有业务请求与实际回答，故障注入的控制指令仍保存在原始Agent报告中，没有送入这个精简评分投影。DeepEval第一次抽取把“类型校验、边界修复、独立检查通过”等未经观察的内容写进outcome，第二阶段据此给1。这是裁判推断错误，不是文件已经完成修复。Ragas两个版本在同一缺证据输入下给0，不能由单例推出框架普遍优劣。

加入首轮真实公开检查后，DeepEval仍给了部分分0.2，但规则已知1001克失败，因此组合为0。两次评分之间没有重跑Agent、没有修正文件。这一差别只能解释为评分输入变化。public_only对有效重量的计费例子通过，输入类型与范围失败，所以原生裁判的部分完成分和完整验收0各有明确含义。

Ragas固定源码在MetricResult中没有传reason，本轮该字段为null；解释在steps最后一次CompareOutcomeOutput.reason中。DeepEval使用固定版本直接measure兼容路径，输入序列化记录；未伪造SDK原生trace。它和官方推荐的observe/full-trace接入分别说明，见[源码导读](source_walkthrough.md)。

## 后补声明式冲突分支的单独实测

完成上述运行后，代码增加显式constraints预检：同一合同同时要求保留原测试与删除所有测试时返回impossible。该分支随后在新的Docker镜像中单独实际执行，断言0次模型请求，报告为conflict_report。旧的两个Agent轨迹与24次裁判没有重写或冒充重跑。原运行镜像中的源码已提取归档，runtime_evidence逐阶段记录镜像与源文件哈希；普通修复分支不受这次增量影响。

这只是一个可判定的声明式矛盾，不能检测任意自然语言目标是否可实现。达到轮数上限、规则审查异常与已知冲突也都不代表完成。完整s17会话恢复、后台defer、模型impossible判断等在后续课程集成核验。
