# 第16课练习

先打开保存的实测报告，完成后再看 [答案](solutions.md)。修改实验时使用新的工作区和报告名，保留原始结果。无需为了做题重新请求模型。

1. 在组合报告里找到公开 Goal 成功、workflow completed 和独立业务通过三种证据。分别说出它们能够证明什么，不能证明什么。
2. 从 `native_traces` 找一条实际 `read_file`，沿 UUID 定位所属 trace。比较同步工具与队友线程的 parent UUID，解释为什么不能把全部独立根手工挂成一棵“漂亮”的树。
3. 对工具投影中两个预期调用、一个实际调用手算覆盖与 F1。解释 DeepEval 默认0.5、exact match为0、Ragas Accuracy为0、F1约0.6667为什么可以同时成立。
4. 第一轮仅规范证据中，DeepEval 有3个 YES、2个 BORDERLINE。按默认和惩罚含糊项两种规则计算，随后到原始报告核对。这个结果能否证明测试已执行？
5. 找出首轮投影里丢失的测试命令。只修改采样层，写出包含工具名、参数与结果的记录，并保留源 span UUID。说明为什么这不是一次新的 Agent 运行。
6. 给 `critical_gate` 输入业务通过、权限失败、覆盖未评分三项。设计一个结果对象，说明哪些项必须拦截。不要用平均分处理关键失败。
7. 使用已保留的 workflow 中断与恢复报告，找出成功写入的两个语义键、恢复新增请求和最终任务状态。若把 schema 或 prompt 改了，为什么不能直接称作同一次缓存命中？
8. 读绑定与认领的并发失败记录，用六行时间顺序重建丢失 owner 的过程。指出修复后的跨进程锁必须覆盖哪些动作，以及持锁执行 Git 的代价。
9. 同一持久队友领第二个任务时，为什么旧审批无效？结合任务 ID、工作版本和 gate 重置行为，写出再次要求审批的正确时机。
10. 一次性 cron 已写入 pending，模型接收前进程退出。重启后应怎样处理？设计一个幂等落盘动作，解释“至少一次交付”与“业务恰好执行一次”的区别。
11. 阅读真实拒绝任务。只检查禁写文件不存在是否足够？列出还应核对的调用 ID、拒绝结果、原文件与 post hook 证据。
12. 为自己的小编程项目交付一份结课协议：任务、知识版本、成功条件、正常/错误/边界案例、业务与状态检查、指标范围、关键门禁、失败保存方式及复现命令。列出尚未验证的能力，不套用运费项目的44条输入作为通用结论。

可选实验：改动评测证据格式时，保留相同 Agent 记录，另冻结一次评分协议。即使新分数没有变好，也解释裁判拆句、证据变化和随机性各自可能造成什么影响。
