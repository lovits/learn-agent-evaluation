# e11: 工具名选对了，事情做对了吗？

[e10](../e10_rag_diagnosis/README.zh.md) → `e11` → [e12](../e12_task_completion/README.zh.md) → … → e16

> 分开看名字、参数、顺序和执行结果。

## 问题

把 source.txt 复制到 delivery.txt，再读回确认。参考路径很短：读取源文件、写入目标、读回目标。

如果把后两步的路径都写成 other.txt，工具名依旧是 read_file、write_file、read_file，目标文件却没有生成。反过来，参数全对，写入也可能因为目标位置已经是目录而失败。

需要先说清“工具用对了”具体在比较什么。

## 解决方案

复用第 2 课的循环和三个具名工具，保留每次调用的 name、arguments、result。构造少量调用轨迹，实际执行，再与参考比较。

![具名调用经过校验与分发，状态和输出进入事件记录](https://lovits.github.io/learn-agent-evaluation/diagrams/e11-tool-flow.png)

同一条轨迹分别按名称、参数、顺序和输出检查。需要语义判断时，再使用 DeepEval 的 Argument Correctness。

![参考匹配与参数语义裁判分别保留结果](https://lovits.github.io/learn-agent-evaluation/diagrams/e11-scoring-flow.png)

## 工作原理

### 先区分决定与执行

[run_case](code.py) 为每组创建独立工作区。默认条件的调用决定来自脚本，但仍交给原 Agent 循环实际执行，文件和错误都由工具产生，没有伪造返回值。

加 `--live` 会让现有模型决定复制任务和权限恢复任务。run.origin 区分真实模型与脚本决定，原始回复、输入和事件一并保存。任务模板与模型实际选择的动作分别记录。

循环和工具实现没有增加能力。已有分发仍是：

```python
output = HANDLERS[name](workspace=workspace, **arguments)
```

文件工具先检查路径是否在工作区内；Bash 沿用原有拒绝规则，不具备同等的文件路径隔离。权限场景明确禁止改用 Bash 绕过，不能把文件工具的边界当成整个执行环境已经完全隔离。

### 把参考写成可比较对象

[sample_for](eval.py) 复用已有运行样本，再填入参考：

```python
ToolCall(
    name=c["name"],
    input_parameters=c["arguments"],
    output=c["result"],
)
```

实际事件成为 tools_called，参考成为 expected_tools。参考是一条指定路线；任务若允许其他合法路线，不能仅凭“不匹配这条参考”宣布失败。

### 常规匹配更像参考覆盖

ToolCorrectnessMetric 默认匹配工具名与类型。本课工具均为普通函数类型，不提供 available_tools，因此没有额外的最优工具选择裁判请求；五种匹配模式都由原生代码计算。

非精确模式为每个参考调用找一个尚未使用的实际调用，累计匹配权重，再除以参考调用数：

```text
常规匹配 = 累计匹配权重 / 参考调用数
```

参考三次、实际完成三次后又多读一次，常规分数仍可能为 1。它没有把所有实际调用都放进分母，所以不能直接叫作“工具调用精确率”，也不能保证没有多余动作。

### 参数比较也可能只得部分权重

要把参数纳入规则，显式选择字段：

```python
evaluation_params=[ToolCallParams.INPUT_PARAMETERS]
```

非精确参数比较按键的并集计算匹配比例。假设写入参数包含 path、content 两个键，只把 path 改错，content 相同，这条写入仍可贡献 1/2。

这只是结构匹配权重，不表示“写文件成功了一半”。最终是不是写到了目标位置，要回到执行结果和文件。

### 考虑顺序，不等于完全相同

`should_consider_ordering=True` 使用加权最长公共子序列：在保持先后次序的匹配中，累计最大权重，再除以参考长度。

参考为“读源、写目标、读目标”，实际先写再读时，可能仍匹配两个有序位置，得到部分分数。完整参考顺序都出现后，即使夹着额外调用，有序匹配也可能为 1。

如果要求长度、每个位置、指定字段全部一致，用 `should_exact_match=True`。本课五种模式分别是：

| 模式 | 比较范围 |
|---|---|
| names | 默认无序参考覆盖，匹配名称与类型 |
| arguments | 再比较输入参数，允许部分权重 |
| ordered_arguments | 参数加权的有序子序列 |
| exact_arguments | 长度、位置与输入参数完全匹配 |
| exact_outputs | 再要求执行输出也与参考相同 |

是否需要唯一序列，由任务决定。不要为了拿满分，强迫所有合理解法都走同一条路线。

### 集合 F1 会看见什么

Ragas ToolCallF1 把“名称＋参数”转换为集合，再求精确率、召回率与 F1。它忽略调用先后，相同调用重复出现也会被去重。

因此，额外读了同一份 source.txt，不一定降低这个集合 F1；增加不同参数或不同工具的额外项才可能形成 FP。若关心重复次数与多余步骤，还要检查保留重复的事件序列。

Ragas ToolCallAccuracy 则先检查名称序列，再比较参数。它与 DeepEval 有序子序列不是同一种“顺序正确”。本课只读其设计与固定源码，不再重复接入评分。

### 参数语义裁判不负责发现所有漏项

ArgumentCorrectnessMetric 按原始问题与实际调用判断每次参数是否合理，不以 expected_tools 作参考。它可以接受语义合理的 Bash 命令，却不能仅靠“观察到的参数都对”证明必要调用没有遗漏。

本课保留逐调用 yes/no 和理由，并核对裁决数量。没有实际调用时，原生指标返回 1；包装层保留 sdk_score，同时将结果标为不适用。必要调用没出现，交给参考覆盖或任务条件判断。

语义分数仍有证据范围。本课汇总短任务调用作回顾比较，不能据此证明每次决策在当时已获得足够信息。严肃的单步评测应使用当时上下文，避免把后来的结果当作先前决策的依据。

### 调用匹配，不代表执行成功

tool_failed 先把 delivery.txt 建成目录。写入工具与参数可以完全匹配参考，实际却返回 error。只有比较 output 或检查文件，才能发现它没有得到预期结果。

权限拒绝又是另一回事：题目要求先尝试文件工具，收到 denied 后不要绕过，改写工作区内的 status.txt 并读回。这里 denied 正是预期结果，不应把所有非 ok 状态都当成 Agent 错误。

合法 Bash 复制则可能正确生成文件，却不匹配“读—写—读”的文件工具参考。工具路线与用户目标必须分开解释。下一课再把产物、行为边界和任务成功条件完整接起来。
