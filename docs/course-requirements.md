# 课程需求与实施范围

这门课的目的，是让读者通过一个逐步长大的编程 Agent，学会完整的 Agent 与 RAG 评测过程，并读懂 DeepEval、Ragas 背后的评测原理。读者会 Python，了解 RAG 和 Agent，希望将知识用于实际项目。

## 最终交付

- 保持已确认的 16 课顺序，按第一、二课的方式，依次完成第三至第十六课。
- 每课交付简洁教材、可运行代码、源码导读、练习与参考解释；样本和实际评测记录另放。
- 最后组合成一个完整的编程 Agent 与评测项目，说明各模块怎样合作，怎样从失败找到原因、做修复并回归。
- 完整项目可在 Docker 中运行，知识库可通过目录挂载；GitHub 保存教材和代码，飞书保存对应云文档。

## 项目与框架各自负责什么

| 依据或工具 | 在课程中的作用 |
|---|---|
| Learn Claude Code | 参考递进编程方式、教材结构与讲解节奏；以最小编程 Agent 为被测对象 |
| Datawhale TinyRAG | 知识库接入、检索与上下文评测的贯穿项目 |
| DeepEval | 全课程唯一实际接入的评测框架；按知识点使用样本、数据集、规则、自定义指标和 LLM 裁判 |
| Ragas | 学习指标、声明判定、聚合、数据集构建和裁判校准的原理，阅读相关文档与源码；不重复接入或重复评分 |
| PocketFlow-Tutorial-Codebase-Knowledge | 从当前课的真实代码组织教材草稿，再核对事实、压缩讲解和润色 |
| humanizer | 润色中文，使讲解自然、具体，保持原意与技术准确性 |

既有任务规则可以先用小函数解释，后续再接入需要的 DeepEval 指标。构造框架样本、运行评分和判断任务是否完成，要分别说清。课程只保留理解评测所需的 Agent 机制，不扩展成完整商业编程产品。

## 教材怎样组织

每课讲透一个核心问题，按这条线展开：

1. **问题**：从一个小任务或具体失败开始，说明已有办法哪里不够。
2. **解决方案**：给出本课需要的最小机制，配上两张紧凑图片。
3. **工作原理**：沿关键代码说明输入、处理、分支与输出；只摘讲必要片段，完整函数有链接。
4. **本课变化**：说明相对上一课增加了什么，以及为什么需要。
5. **试一下**：给读者少量有辨别力的观察任务或练习。
6. **接下来**：自然引出下一课。

语言和内容组织参考 Learn Claude Code：简洁、具体、逐步展开，让读者能顺着代码理解机制。少写口号、类比和重复小结；不在正文放制作过程、环境准备、启动服务要求、成绩表或验收报告。根 README 介绍整个课程的大纲和学完能做什么。

源码导读另外说明本课调用链，以及 DeepEval、Ragas 对应文档和固定版本源码中的输入字段、判据、模型裁决、聚合公式与适用边界。正文和源码必须相符，不把两个框架中同名指标当成完全一样。

## 配图要求

每课主教材直接显示两张 SVG 矢量图：一张解释本课关键机制或数据流，一张解释评测过程或运行与评分的代码关系。参照 Learn Claude Code 的原生 SVG 方式，用纯 SVG 文字、浅色节点和箭头解释流程；保持紧凑布局。

- 不使用 Archify，不增加交互页面入口。
- 图片保持适中，图内文字只比旧版略大：节点以 16、连线以 14 为参考，不为加大文字而放大整张画布。
- 节点写清动作、输入和输出；有判断时标明条件与分支，最后说明得到什么判断或数据。
- 两张图放在解决方案附近，源码导读不重复堆图。
- SVG 源文件随仓库保存，GitHub 正文直接显示矢量图，本地阅读映射回同一 SVG；飞书使用按同尺寸3倍像素导出的 PNG，显示宽度保持适中。保留原有结构源图，避免图中文字依赖 foreignObject。
- 发布后直接打开 GitHub 对应教材页，确认每课恰有两张图片，实际加载成功；本地存在图片不算完成这一步。

## 代码原则

少即是多。每课只引入解释当前知识点所需的代码，后续复用已经讲过的能力。先有可运行的小机制，再逐步组合；不在第一课贴完整 Agent，不为展示框架接口复制两套业务逻辑。

代码、评测脚本和教材片段必须对应。规则能直接判断的事项，优先用明确规则；需要理解自然语言时，才引入相应裁判。区分提出动作、执行动作、执行成功和完成任务；保留实际调用参数、返回结果与产物。

知识库挂载后，要记录检索结果与最终交给模型的上下文，不能把工具输出随意当成检索证据。缺少参考时保留缺失状态，不拿实际答案冒充参考。

## 16 课的范围

| 课 | 一个核心知识点 | 必要的实现或观察 |
|---|---|---|
| 01 | 定义成功 | 最小 Agent 循环和 Bash；独立检查实际记录与文件 |
| 02 | 保存一次运行 | 具名工具、必要权限、事件记录；生成一份 DeepEval 样本 |
| 03 | 准备评测数据 | 任务与参考、来源、候选审核、去重、题族与开发/留出划分 |
| 04 | 给样本评分 | 规则与 LLM 裁判、rubric、结构化裁决、阈值与评分失败 |
| 05 | 接通知识库 | TinyRAG 与只读挂载；文档、分块、检索结果、最终上下文的去向 |
| 06 | 上下文相关性与排序 | 资料是否相关，相关资料是否排在前面；precision 与排序聚合 |
| 07 | 上下文覆盖与召回 | 参考事实有没有被找到；漏证据与 recall |
| 08 | 回答对上下文的忠实度 | 拆解声明，判断支持、矛盾或未提及，并解释分数 |
| 09 | 答案质量 | 切题、事实正确、完整与合理拒答；相似度的用途和边界 |
| 10 | 上下文干扰与故障定位 | 控制噪声或缺失证据，区分资料、检索和生成问题 |
| 11 | 工具调用质量 | 工具名、参数、顺序、重复和漏调用；明确评分单位 |
| 12 | 任务完成度 | 用独立产物或业务状态判断交付结果，结合必要语义标准 |
| 13 | 会话上下文与约束保持 | 用户修改要求后，保留有效约束并评价多轮目标 |
| 14 | 校准 LLM 裁判 | 人工标签、分歧、误接收与误拒绝、偏差与留出验证 |
| 15 | 比较两个版本 | 固定同题配对比较、分层失败、不确定性、延迟与费用 |
| 16 | 综合项目与持续回归 | 组合既有能力，失败补题、最小修复、重评与回归 |

“上下文评测”主要在第 5—7 课展开，第 8—10 课继续观察上下文对回答的影响。数据集在第 3 课建立，之后各课补充对应任务，不另造一套无关数据平台。每课更细的知识点、实验与学会的标志，以[完整大纲](curriculum.md)为准，不重新删减已确认的核心范围。

## 逐课实施与完成条件

实施顺序：先修好第 1、2 课并核对 GitHub 中四张图片全部加载；再将全部需求与完整大纲整理成文档并读回核对；随后使用 define-goal 设置目标，以本文、完整大纲和制作规范为依据，依次完成第 3—16 课及综合项目。

按第 3 → 4 → … → 16 课依次制作，不同时堆出全部空目录或只写提纲。每课先读当前大纲、相关上游代码与官方/飞书资料，确定一个核心问题；实现最小代码和评测样本，再用 PocketFlow 组织草稿、核对并润色，最后完成配图、Docker 验证和远端同步。

一课完成应同时满足：讲解覆盖已确认范围；关键代码可运行且与正文一致；样本说明能解释得分依据；Docker 中相关场景实际跑通；GitHub 教材的两张 SVG 成功显示；飞书文档同步后重新读取核对。软件检查、真实模型执行和受控示例分别记录。

教学例子可以人工构造，但必须标明；真实运行和评分结果不得编造，不把接口异常记成有效零分，也不把历史运行写成新结果。主教材讲原理，评测记录负责提供证据。

全部完成时，读者应能独立为自己的 Agent 准备数据、选择判据、运行评测、解释失败、比较版本，并将修复接入持续回归。遇到会改变课程范围或关键教学目标的歧义，再通过逐轮提问澄清；已有要求不反复询问。
