# e10: 答案错了，先改哪一层？

[e09](../e09_answer_quality/README.zh.md) → `e10` → [e11](../e11_tool_quality/README.zh.md) → … → e16

> 沿阶段记录，找证据最早在哪里发生变化。

## 问题

回答没有给出正确发布命令。可能是知识库缺少规范，也可能是检索没找到，或者已经找到了，却没被送进模型。

这几种情况最终都可能只剩日志资料。只看回答或一份上下文，无法区分它们。直接修改生成提示词，未必改到了发生问题的位置。

## 解决方案

固定第 9 课真实运行中的检索查询，分别保存资料快照、原生候选、检索输出和实际上下文。每次只在一个位置改动，再重放同一个生成环节。

![从知识库到生成回答，保留各阶段快照](https://lovits.github.io/learn-agent-evaluation/diagrams/e10-pipeline-flow.png)

先检查目标证据在哪里缺失或版本不符，再看回答怎样使用资料。诊断输出表示下一步先查哪里，不能代替完整的根因分析。

![沿来源、检索与组装逐层检查证据缺口](https://lovits.github.io/learn-agent-evaluation/diagrams/e10-diagnosis-flow.png)

## 工作原理

### 相似的上下文，可能来自不同阶段

[prepare](code.py) 从已校验哈希的真实记录中取出固定查询，用 TinyRAG 检索当前资料快照。基线保存三个候选，选择前两个作为上下文。

几种控制条件分别改变不同位置：

| 条件 | 改动位置 | 保留什么用于核对 |
|---|---|---|
| source_missing | 检索前从内存快照移除发布规范 | 资料清单与实际候选 |
| retrieval_miss | 原生检索后过滤掉发布规范 | 原生候选与过滤后输出 |
| assembly_drop | 检索输出不变，组装时移除规范 | 命中结果与实际上下文 |
| stale_source | 快照中将命令改成教学旧版本 | 内容哈希与当前参考 |
| noise | 组装后追加无关天气备忘 | 原上下文与追加内容 |
| conflict | 组装后追加相反的旧备忘 | 两种来源与优先级 |

这些是受控条件，不是声称发现了六起真实故障。挂载的原始资料没有被删除或改写；移除和旧版本都发生在内存快照中。

检索漏召回条件尤其要分清：

```python
native_hits = retrieve(query, limit=3, documents=documents)
retrieved = [p for p in native_hits if p["path"] != source_path]
```

这里故意过滤了检索输出，不声称 TinyRAG 的这次原生查询自然漏召回。组装遗漏则发生在更后面：

```python
selected = retrieved[:2]
selected = [p for p in selected if p["path"] != source_path]
```

两个片段仅展示各自条件下的核心操作，完整分支见代码。没有阶段记录，就容易把组装问题归到检索器头上。

### 先查第一个可观察缺口

[first_gap](eval.py) 按顺序检查来源：

```python
if document is None:
    return "source_missing"
if document["sha256"] != source["sha256"]:
    return "source_version"
```

存在且版本符合参考，才继续检查是否进入检索输出、是否被保留在 selected 中。

哈希不同只说明内容与参考绑定的版本不一致。可能是资料过期，也可能是资料正确更新、参考还没更新，需要先审核变更。本课旧版本是明确构造的错误命令，不能把这种结论推广到所有哈希变化。

返回 None 表示这些检查没有发现目标来源丢失，不表示回答正确。本课规范很短，完整落在一个片段中；长文档只命中路径，还需要继续核对具体证据位置。

证据缺口也不一定导致差回答。资料不足时，模型可以恰当拒答。要分开看链路状态与最终行为。

### 只重放生成，避免模型重新检索

[replay](code.py) 深拷贝真实 Agent 最后一次生成输入，用当前条件替换知识结果：

```python
results[0]["output"] = {
    "knowledge_version": row["knowledge_version"],
    "contexts": row["contexts"],
}
response = call_model(messages, tools={})
```

每个条件都附加同一条资料策略：按给定资料回答，缺失时不猜测；发生冲突，以 atlas/release.md 为当前主规范。回放不允许新工具调用，否则模型可能重新搜索，改变我们正在比较的上下文。

这是生成环节的真实模型调用，不是重新运行完整 Agent。原始轨迹保持不变；新的 model_input、原始模型返回和回答分别保存。参考答案只交给评测方，没有补进生成输入。

### 忠实于旧资料，仍可能回答错误

stale_source 保留发布规范的路径，却把命令改为 unittest。模型若照着它回答，可能对本次上下文很忠实，却不符合当前参考要求。

本课复用两项 DeepEval 评分：

```python
row["faithfulness"] = judge_faithfulness(sample, model)
row["task_quality"] = score(task_metric(model), sample)
```

前者沿第 8 课保留声明、资料事实与裁决，默认分数仍允许 borderline 通过；后者沿第 9 课检查正确、完整与证据不足时的行为。两者与阶段记录一起读，不能把忠实度当作资料版本正确的证明。

### 无关资料与冲突资料不同

天气备忘不回答发布问题；旧备忘却给出了另一条命令，甚至允许失败后发布。后者需要明确的来源优先级。

模型若按当前规范回答，而忠实度指标把新旧资料混成一组 truths，裁判仍可能遇到矛盾。此时要检查它是否保留来源、是否理解优先级，不能看到低分就认定 Agent 选错了规范。

本课的优先级来自题目规定，不是“文件名看着更新就相信它”。实际项目需要有可靠的版本、适用范围和来源规则。

### Noise Sensitivity 不是新旧分数之差

Ragas 的 Noise Sensitivity 从单条回答出发，判断哪些声明未被参考支持，却被某类上下文支持。它先按参考把资料分为两类：至少支持一条参考声明的资料算 relevant，其余算 irrelevant。

然后对每条回答声明检查：参考是否支持、相关资料是否支持、无关资料是否支持。相关方向统计“参考未支持但相关资料支持”；无关方向还排除同时得到相关资料支持的声明，避免重复归入两类。

```text
relevant   = 相关资料支持的未获参考支持声明数 / 全部回答声明数
irrelevant = 仅无关资料支持的未获参考支持声明数 / 全部回答声明数
```

分数越低，说明这类错误支持关系越少。它不是添加噪声前后答案得分的差，也不单独证明某段资料导致了错误。

[noise_fraction](eval.py) 用三组明确标注的布尔数组展开聚合。手算例子有三条声明：一条正确、一条未被参考支持且两类资料都支持、另一条仅无关资料支持。两个方向均为 1/3；分母不是两条错误声明。

这些数组只是算式示例，没有冒充真实回放的语义裁决，也没有运行 Ragas。参考遗漏真实事实时，“未获参考支持”也未必等于客观错误。

### 一次对照能说明多少

追加噪声后回答不变，只说明这次、这段噪声没有观察到质量下降。单次回放也受模型随机性影响，分数差不能直接当成稳定因果效果。

Noise Sensitivity 为 0 只表示未命中对应的归因条件，不代表没有遗漏或回答已完成任务。空声明的分母未定义，本课辅助算式返回 None；边界处理与框架原实现分别见[源码导读](source_walkthrough.md)。

## 本课变化

没有新增 Agent 平台。只增加阶段快照、少量受控改动和生成回放，复用已有检索、模型传输与 DeepEval 评分。各阶段证据与模型结果分别保留，错误和未定义结果也不填成有效零分。
