## 按需加载：先找目录，再把正文交给模型

这里借鉴了 Learn Claude Code 固定版本中 `SkillLoader` 的一个思想：内容需要时才交给模型。上游实现会扫描技能、解析前置元数据并按名称加载正文；本课只借用“按需提供内容”的组织方式，没有完整移植技能前置元数据、注册系统或执行指令。

调用形式很简单：

```python
hits = search_knowledge(
    "POST upload API token size limit"
)
```

返回至多三篇文档。每项包含：

```python
{
    "id": "e04/auth.md",
    "text": "...",
    "sha256": "...",
    "matches": 4,
}
```

这里要区分两个视角：检索器为了计算匹配分数，会从磁盘读取候选文件；模型只会看到最终返回的前三篇。所谓“按需加载”，不是磁盘完全不读其他候选，而是避免把整个知识库正文全部塞进模型上下文。

检索轨迹也会保留这次工具调用、参数、权限结论、命中文档和模型后续动作。因此我们既能检查最终答案，也能回答“它到底读过哪些来源”。

## 这个检索器具体怎样工作

知识库是小型、合成的项目规范集合，不是生产知识库。规则刻意保持简单：

1. 递归读取 Markdown 和文本文件。
2. 英文按单词切分，统一为小写。
3. 连续中文按相邻双字切分。
4. 计算查询与文档的词项交集数量。
5. 交集多的排在前面；同分时按路径排序。
6. 只返回前三篇。

核心排序可简写为：

```python
hits = [
    {**doc, "matches": len(query_terms & terms(doc["text"]))}
    for doc in catalog(root)
]
```

```python
return sorted(
    (x for x in hits if x["matches"]),
    key=lambda x: (-x["matches"], x["path"]),
)[:3]
```

这只是词面交集检索。它不理解同义词，也不能声称是语义检索或生产级 RAG。

每个文件就是一个证据单元。`id` 使用相对路径，例如 `e04/limits.md`；`sha256` 是正文内容的版本指纹。同一路径的内容发生变化，哈希也会变化，所以评估时不能只记录路径。

`KNOWLEDGE_DIR` 在容器中映射为只读的 `/data/knowledge`。更换宿主机目录不需要重建镜像：

```sh
KNOWLEDGE_DIR=/绝对路径 docker compose run --rm -T --entrypoint python course -c 'from lessons.e04_retrieval.code import search_knowledge; print(search_knowledge("你的查询词"))'
```

请把 `/绝对路径` 换成真实存在的目录，不要原样执行占位符。真实实验曾换挂载后检索到 `alternate.md` 和 `2097152` 字节，且没有重建镜像；文本变化后哈希也随之更新。

## 验收为什么要独立进行

真实 Agent 会按需检索两篇资料，再把三个事实和来源路径写入 `upload_notes.txt`。独立的 [verify.py](verify.py) 在断网环境运行，工作目录只读；它读取真实文件和轨迹，检查：

- Agent 是否正常结束；
- 轨迹结构是否有效；
- 文件是否包含认证、`1048576` 和 `413`；
- 两篇必要来源是否确实被检索；
- 文件内容是否与报告记录一致。

模型不知道这份验收标准，独立标准也没有挂载给这个具体 Agent。不过教学镜像同时包含教材例题，因此不能把环境称为严格盲测。

真实 Agent 任务与 `good`、`late`、`missing`、`empty` 是两类数据。前者是真实检索和写文件任务；后四者是人为控制的检索扰动，不能冒充四次 Agent 自然输出。

## 用文档 ID 计算精度与召回

先把返回 ID 去重；重复 ID 保留第一次出现的位置。

ID 精度表示“返回的资料中，有多少确实相关”：

> ID 精度 = 找到的相关 ID 数 ÷ 返回的去重 ID 数

ID 召回表示“应找到的资料中，找到了多少”：

> ID 召回 = 找到的相关 ID 数 ÷ 标注的相关 ID 数

例如返回认证、限额和一篇界面主题资料，前两篇相关：

- ID 精度为 `2/3`
- ID 召回为 `2/2 = 1`

如果只返回认证文档：

- ID 精度为 `1`
- ID 召回为 `1/2 = 0.5`

这说明“返回的全都相关”不等于“必要证据已经找全”。

已知相关标注非空但返回为空时，本课把所有规则分数记为 `0`。如果标注集合本身为空，则召回没有定义，程序会报错；不能把“没有标注”当成满分。参考标注若漏掉必要文档，还会让召回虚高。

## 排序质量：AP、MRR 与二元 NDCG

精度和召回只看集合，不关心顺序。可是模型通常先读排在前面的内容，所以排序也应评分。

`AP_retrieved` 在每个相关位置计算截至该位置的精度，再求和，最后除以“本次返回中的相关项数”。`AP_reference` 使用相同分子，但除以“全部标注相关项数”。前者主要评价已返回相关项的排列，后者还会惩罚漏检，二者不能混用同一个名字。

假设两篇相关文档和一篇噪声原本排列为：

```text
[相关, 相关, 噪声]
```

此时 `AP_retrieved = 1`。把噪声移到开头：

```text
[噪声, 相关, 相关]
```

相关项分别位于第2、3名：

- 第2名精度是 `1/2`
- 第3名精度是 `2/3`
- 平均为 `(1/2 + 2/3) / 2 = 7/12 ≈ 0.5833`

两种排列的 ID 精度仍是 `2/3`，ID 召回仍是 `1`，但 AP 明确下降。

MRR 只看第一个相关项的位置，分数为其名次的倒数；越靠前越好。二元 NDCG 将相关性记为 `0/1`，第 `rank` 位按 `1/log2(rank+1)` 折扣，再除以相同返回长度和相关总数下的理想 DCG。AP、MRR、NDCG 都是高分更好，但关注点和分母不同。

## 文档召回不能代替声明召回

参考答案含三条声明：

1. 使用 `X-Project-Token`
2. 最大文件大小为 `1048576` 字节
3. 超限返回 `HTTP 413`

必要文档只有认证和限额两篇。因此只返回认证文档时，ID 召回是 `1/2`；如果裁判只确认第一条声明有依据，声明召回约为 `1/3`。

ID 数量与声明数量是不同单位，不能直接视为同一量表。类似地，只返回认证时：

- ID 精度为 `1`
- ID 召回为 `0.5`
- `AP_retrieved` 为 `1`
- `AP_reference` 为 `0.5`

这组数字正好说明：所有返回结果都相关，仍然可能漏掉完成任务所需的证据。

## 原生 SDK 怎样裁决上下文

本课实际运行了 DeepEval 的三个指标，以及 Ragas `metrics.collections` 中两个带参考口径的指标。版本和官方链接见 [source_walkthrough.md](source_walkthrough.md)。

DeepEval 的共同过程是：构造提示词与结构化模式，调用裁判模型，校验响应，保存逐项裁决，再聚合为分数。同步入口是 `measure`，异步入口是 `a_measure`；本实验使用同步入口。阈值 `0.7` 只是教学约定，不是官方推荐的业务门槛。

`ContextualPrecision` 让模型判断每篇上下文对问题和参考答案是否有用，然后对相关位置的累计精度求平均。其分母是本次返回中的相关节点数，与 `AP_retrieved` 方向一致。

`ContextualRecall` 把参考答案拆为声明，再判断每条声明能否归因到检索上下文。它统计声明，不统计文档，所以认证单篇对应的结果可能约为 `1/3`。

`ContextualRelevancy` 不要求参考答案。它从每篇内容中提取声明，判断这些声明是否与问题相关，再把裁决展开聚合。它衡量的不是文档级 ID 精度，也没有排序折扣。三篇内容重排后实测分别为 `0.6667` 和 `0.7143`，差异来自模型分句与裁决波动；不能据此推断排序提高了 Relevancy。

Ragas 实际运行了：

- `ContextPrecisionWithReference`
- `ContextRecall`

适配器继承 `InstructorBaseRagasLLM`，把宿主机返回的 JSON 按 `response_model` 校验；没有拿第3课旧式模型接口冒充现代 `collections` 接口。其异步调用简写如下：

```python
async def agenerate(self, prompt, response_model):
    return await asyncio.to_thread(
        self.generate, prompt, response_model
    )
```

Ragas 精度聚合的分母带有 `epsilon`，所以理论上的 `1` 可能保存为接近 `1` 的小数；报告保留实际值，不强行改写。

`ContextPrecisionWithoutReference` 只做了源码对照，没有运行原生模型实验。它以 `response` 代替 `reference`，仍然依赖回答；回答若漏掉认证要求，认证资料也可能被判为无帮助。因此不能称它完全不依赖答案，更不能宣称本课实测过它。

`empty` 在原生 SDK 层明确记为 `skip`，规则层才记 `0`。这不是伪造一个 SDK 的零分：Ragas Recall 会拒绝空上下文列表。

最终受控实验结果如下：

| 情景 | ID精度 | ID召回 | AP（本次相关） | DeepEval精度 | DeepEval召回 | DeepEval相关性 | Ragas精度 | Ragas召回 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| good | 0.6667 | 1.0 | 1.0 | 1.0 | 1.0 | 0.6667 | 1.0 | 1.0 |

| missing | 1.0 | 0.5 | 1.0 | 1.0 | 0.3333 | 1.0 | 1.0 | 0.3333 |
| empty | 0.0 | 0.0 | 0.0 | skip | skip | skip | skip | skip |

初次 Agent 入口残留了第2课的故障注入提示，模型多发出一个无关的 Bash 请求，并被权限系统拒绝。清理提示后重跑成功。两轮 Agent 共进行 `8` 次模型请求。

初次 SDK 裁判本身完成，但保存器把 Relevancy 的 `verdicts_list` 错当成 `verdicts`，于是有 `3` 项保存错误；这不是模型错判。修复后完整重跑，最终 `23` 次裁判请求、`0` 个指标运行错误。两轮 SDK 共 `46` 次裁判请求，教材生成器调用另计。

完整 JSON 保存了原始提示词、响应、裁判 verdict 和 Agent 工具事件。规则结果、原生分数与判分器运行错误彼此分开：`score=0` 是有效低分，`score=null` 加错误信息才表示没有成功评分。

## 练习与验收标准

完成 [exercises.md](exercises.md) 中的练习，至少应能独立解释：

- 为什么 `[噪声, 相关, 相关]` 的 AP 是 `7/12`；
- 为什么只返回认证时，ID 召回是 `1/2`，声明召回却可能是 `1/3`；
- 为什么相同 ID 仍要检查 `sha256`；
- 重复 ID、空结果、空标注和参考漏标分别怎样处理；
- 为什么 `WithoutReference` 不能替代完整参考下的召回评价。

最终验收以三条命令为准：真实 Agent 正常完成、独立验证全部通过、评价实验报告 `23` 次裁判请求且 `0` 个指标错误。

这些结果来自小型合成数据和单次开发实验，不能证明检索器或裁判模型在任意知识库上都可靠。本课也没有评价最终回答的事实忠实性；Faithfulness 留到第5课讨论。现在应掌握的边界是：检索到了什么、漏掉了什么、相关证据排在何处，以及每个分数究竟使用什么单位和分母。
