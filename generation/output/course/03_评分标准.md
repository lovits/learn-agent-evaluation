# e03: 评分标准 — 同一个 48，为什么分数不同

> 先确定在判断什么，再选择评分器。

## 字面不同，含义相同

Agent 修改程序以后，可能返回：

```text
{"result":48}
```

也可能返回：

```text
程序输出为四十八。
```

如果接口只接受 JSON，第二句不合格；如果只问输出是多少，两句都表达了正确数字。还有第三种情况：回答写了48，程序却根本没改。

格式、含义和实际完成状态，要各自有标准。本课保持 Agent 不变，只增加评分层。

## 能直接判的条件，先写规则

[`rules`](https://github.com/lovits/learn-agent-evaluation/blob/main/lessons/e03_judges/code.py) 先比较原始字符串，再解析 JSON：

```python
value = json.loads(case["response"])
valid = (
    isinstance(value, dict)
    and set(value) == {"result"}
    and type(value["result"]) is int
    and value["result"] == 48
)
```

这里判断的是整个输出合同：对象只有 `result`，类型是整数，值是48。用 `type(...) is int` 可以排除布尔值。

程序还单列 `state_contract`，读取独立检查给出的状态。教学样本通过构造这个字段制造差异；实际项目中，它必须由文件和执行检查产生。

## 比较集合，要先看分母

预期工具为四种，实际只使用其中两种。精确率回答“用了的有多少合适”，召回率回答“该用的覆盖多少”：

```python
overlap = len(expected & actual)
precision = overlap / len(actual) if actual else 0.0
recall = overlap / len(expected) if expected else 0.0
f1 = 2 * precision * recall / (precision + recall) if precision + recall else 0.0
```

在这个手算例子中，precision 为1，recall 为1/2，F1 为2/3。

`set_f1` 先去重，因而忽略顺序、参数和重复次数。它只适合解释覆盖。后面的工具课会把这些条件分别加回来。

## 理解含义时，把标准交给模型

LLM 裁判需要一份 rubric，也就是明确的评分依据。本课要求它判断：回答是否表达输出为48，是否符合独立状态，并忽略 JSON 格式。

DeepEval 的 G-Eval 接受显式评分步骤：

```python
GEval(
    name="Evidence-aware answer",
    evaluation_steps=[CRITERION],
    evaluation_params=params,
    model=model,
    threshold=0.7,
    async_mode=False,
)
```

`evaluation_params` 决定裁判能看见哪些字段。`evaluation_steps` 决定按什么标准看；`threshold` 决定分数达到多少才接受。

例如“不能虚报完成”可能被理解为只禁止出现“完成”二字。若业务要求独立检查失败时一律不能通过，就应把这条写清楚。标准中的歧义会成为评分中的歧义。

## 三种裁判怎样组织判断

| 方式 | 判断过程 | 输出含义 |
|---|---|---|
| G-Eval | 按步骤给出评分与理由 | 归一化后的等级分 |
| DeepEval DAG | 判断节点选择分支，落到分值叶子 | 由路径决定的分数 |
| Ragas AspectCritic | 按 `definition` 判断是否满足 | 二元裁决 |

DAG 的分值映射由程序固定，判断节点仍可使用模型。把判断接成图，并不会消除模型的不确定性。

本课的 G-Eval 适配器没有 token 级概率，因此走结构化评分路径。AspectCritic 使用固定版本的旧接口，`strictness=1`。它们的具体调用链见[源码导读](https://github.com/lovits/learn-agent-evaluation/blob/main/lessons/e03_judges/source_walkthrough.md)。

## 0 分和没有分数

裁判正常返回“不满足”，是有效的0分。请求失败或结果无法解析，则没有形成裁决：

```python
except Exception as error:
    scores[type(metric).__name__] = {
        "score": None,
        "error": str(error),
    }
```

统计时要同时保留未评分项。把它们删掉，会让结果看起来比实际更可靠。

## 从规则函数读起

`rules` 分别返回 `exact_match`、`json_contract`、`state_contract` 和工具集合分。它们对应不同条件，不能互相代替。

`set_f1` 明确选择空集合约定：双方都为空时为1，仅一方为空时为0。先确定任务是否需要工具，再决定这个分数有没有业务意义。

## DeepEval G-Eval

[官方说明](https://deepeval.com/docs/metrics-llm-evals) · [g_eval.py](https://github.com/confident-ai/deepeval/blob/34db63dd005ebc9a905c8ef4741ae0687c93c14c/deepeval/metrics/g_eval/g_eval.py)

```text
measure
  → _validate：检查 evaluation_params 对应字段
  → _generate_evaluation_steps：复用显式步骤或生成步骤
  → _evaluate：组织样本与评分要求
  → generate_rubric_score：请求评分和理由
  → 按 score_range 归一化
```

提供 `evaluation_steps` 可以固定本次标准，减少一步标准生成。自定义 `DeepJudge` 接收 prompt 与 schema，再把模型文本恢复为结构化对象。

原生评分工具会尝试支持概率的路径，不支持时进入 schema 路径。本课适配不提供 logprobs，不能把这个等级分解释成概率加权结果。阈值0.7是示例政策，需要在具体任务上校准。

## DeepEval DAG

[官方说明](https://deepeval.com/docs/metrics-dag) · [dag.py](https://github.com/confident-ai/deepeval/blob/34db63dd005ebc9a905c8ef4741ae0687c93c14c/deepeval/metrics/dag/dag.py)

图先检查节点关系和必需字段，再执行根节点。本课用一个 `BinaryJudgementNode`：真分支指向10分叶子，假分支指向0分叶子，最后归一化。

确定的是路径到分值的映射；模型节点的判断仍可能变化。`include_reason=False` 省略额外总结，节点裁决仍可保留用于解释。

## Ragas AspectCritic

[官方说明](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/aspect_critic/) · [_aspect_critic.py](https://github.com/vibrantlabsai/ragas/blob/8c63f10d500c44efbf24fdb9e2920de2104c321c/src/ragas/metrics/_aspect_critic.py)

```text
single_turn_ascore
  → AspectCriticInput(user_input, response)
  → prompt.generate
  → AspectCriticOutput(reason, verdict)
  → _compute_score
```

`definition` 进入提示，结果是0或1。固定版本此路径把一次生成结果交给聚合函数，不能仅凭 `strictness` 属性推断执行了多次独立投票。

## 适配器只连接接口

`DeepJudge` 与 `RagasJudge` 负责模型传输及对象转换，评分 prompt 和聚合由原生 SDK 负责。后续 collections 指标要求另一套现代 Ragas 接口，要按所用类的签名接入。

保存原始理由有助于排查“标准不清”和“裁判误解”。错误、有效零分和未定义结果分别记录；已看过的样本用于修订标准后，还需要留出样本验证。
